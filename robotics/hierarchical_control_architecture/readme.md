
ロボット制御では姿勢や動作をつかさどるアクチュエータの制御もあれば、周辺状況を集めて回って次の動作を決める制御もあります。
前者は短期間で次々と指示が必要ですが、後者はマルチセンサから収集した情報を複雑なアルゴリズムを使って計算を行う重い処理です。
この性格の異なる処理を同じ計算機で計算させるかというと、Noです。
計算機を上位と下位に分けることが一般的です。
今日はそんな計算機を分散させるアーキテクチャについて説明していきます。

## アーキテクチャ

典型的な構成は以下のように上位計算機と下位計算機の分割です。

| 層 | 役割 | ハードウェア例 |
|----|------|---------------|
| **上位計算機** | 画像処理・SLAM・経路計画・AI推論 | NVIDIA Jetson、Raspberry Pi 5、x86 PC |
| **下位計算機** | アクチュエータ制御・センサ読み出し・安全監視 | Arduino、Teensy、STM32、ESP32 |

このように計算機を分割するアーキテクチャを **階層型制御アーキテクチャ（Hierarchical Control Architecture）** と呼びます。

### なぜ分けるのか

- **リアルタイム性**：アクチュエータ制御はミリ秒単位の厳密なタイミングが必要。画像処理の重い計算がそのタイミングを乱すことを防ぐ
- **安全性**：上位計算機がフリーズしても、下位計算機が緊急停止や姿勢勢維持を継続できる
- **負荷分散**：画像認識（GPU負荷）とモーター制御（GPIO/タイマー負荷）を別ハードで処理

### 通信の例

上位と下位を **ROS2**、**CAN**、**EtherCAT**、**UART** などで接続します。

```
[NVIDIA Jetson: カメラ画像→物体検出→目標位置生成]
              ↓ (ROS2 / Twistメッセージ)
[Teensy 4.1: モーターPID制御・IMU読み取り・緊急停止]
              ↓
        [モータードライバ・サーボ]
```

### 一言でまとめると

> **「脳（認知・判断）と脊髄（運動制御）を別の計算機に分ける」** 設計が標準的に使われています。**

## 階層型制御アーキテクチャでない場合

単一の計算機で「重い画像処理」と「アクチュエータのリアルタイム制御」の両方を同時に行うと、以下のような不具合が起こります。

### 比喩で理解する

**「運転中に、運転手が自分でナビの経路計算もしている」** 状態です。

- 交差点で「右折か左折か」を深く考えている間に、ハンドル操作をミスる
- ナビの計算に夢中になって、ブレーキのタイミングを1秒遅らせる
- 前方の歩行者を認識する処理が重くて、ステアリングの制御がカクカクになる

ロボットでも同じことが起こります。

### 具体的に起こる不具合

__1. 制御周期の乱れ（ジッター）__

アクチュエータ制御は**一定周期**（例：1msごと）で実行される必要があります。しかし、画像処理のような重いタスクが実行中は、OSが制御タスクを「後回し」にします。

```
理想:  制御→制御→制御→制御→制御 （1ms間隔）
実際:  制御→制御→[画像処理で50ms停止]→制御→制御
```

**結果**：モーターのトルク更新が遅れ、振動や追従遅延、最悪の場合は転倒が発生します。

__2. 緊急時の反応遅れ__

障害物検知や転倒検知などの**緊急停止処理**は、ミリ秒単位で応答する必要があります。しかし、重い処理がCPUを占有している間は、緊急処理が実行されません。

**例**：AGVが人を検知したのに、画像のセマンティックセグメンテーション処理が終わるまでブレーキがかからない。

__3. ガベージコレクション（GC）による停止__

Python や Java などの言語では、メモリ整理のための GC が発動すると、**数十〜数百ms 一切の処理が停止**します。

```
通常運転中... → [GC発動: 100msフリーズ] → モーター制御が100ms分飛ぶ
```

**結果**：ドローンなら姿勢が崩れ墜落、マニピュレータなら目標軌道から大きく外れる。

__4. センサーデータの喪失__

IMUやエンコーダからのデータは、一定間隔で読み取る必要があります。CPUが画像処理に占有されている間、センサーバッファがオーバーフローして**データが失われます**。

**結果**：「今の関節角度が分からない」状態になり、逆運動学の計算が狂い、機械に衝突する。

### シナリオで見る不具合

| ロボット種別 | 階層分離なしの不具合 |
|-------------|---------------------|
| **ドローン** | カメラ画像のAI推論中にGCが発生 → 100ms制御が止まる → 姿勢崩れて墜落 |
| **マニピュレータ** | 物体認識処理にCPUが奪われる → 1ms周期の軌道追従が遅延 → 作業対象に衝突 |
| **AGV** | LiDAR+カメラのSLAM計算中 → 緊急停止信号が処理されない → 人に衝突 |
| **四足歩行** | 地形認識の深層学習推論中 → 足先の力覚制御が途切れる → ふらついて転倒 |

## 階層型制御アーキテクチャの実例

実際の階層型制御アーキテクチャの例を挙げるとするとこんな感じとなります。
いずれも現実世界で状況判断を伴う重い処理と、止めてはならない動作が分かれることを示します。

### 例1: ドローン（PX4 + Raspberry Pi / NVIDIA Jetson）

産業用・研究用ドローンで最も標準的な構成です。

| 層 | ハードウェア | 行っていること |
|----|-------------|-------------|
| **上位** | Raspberry Pi 5 / Jetson | カメラ画像からの物体検出、GPS経路計画、SLAM、AIによる目標追跡 |
| **下位** | Pixhawk（STM32マイコン、PX4ファームウェア） | 1000HzでのモーターPID制御、姿勢安定化、緊急時の自動着陸、バッテリー監視 |

**通信**: MAVLink（シリアルまたはEthernet）

- 上位が「あの赤い標的を追いかけて」と目標速度を送信
- 下位が「1msごとにモーター出力を調整して姿勢を保つ」を独立に実行
- 上位がフリーズしても、下位は「ホバリング維持」または「自動着陸」を継続

### 例2: 産業用ロボットアーム（Fanuc / ABB / UR）

工場の溶接・組み立てラインで使われる構成です。

| 層 | ハードウェア | 行っていること |
|----|-------------|-------------|
| **上位** | 産業用PC / 教示盒（タブレット） | 作業プログラムの実行、3Dビジョンによる部品位置認識、衝突回避の経路計画 |
| **下位** | 各関節のサーボドライバ / 安全PLC | 各関節の位置・速度・トルクのリアルタイム制御（通常1kHz〜8kHz）、緊急停止回路、過電流保護 |

**通信**: EtherCAT / CANopen

- 上位が「部品Aの穴にピンを差し込む軌道」を計算
- 下位が「各モーターを0.125ms周期で追従させ、外乱があれば即座に補償」
- 人が近づいた場合、下位の安全PLCが即座に電源遮断（上位の判断を待たない）

### 例3: 自動運転車（Tesla / Waymo / 一般車のADAS）

| 層 | ハードウェア | 行っていること |
|----|-------------|-------------|
| **上位** | 車載コンピュータ（x86/GPU） | カメラ・LiDAR・レーダーの融合、周囲車両の行動予測、経路計画、深層学習推論 |
| **下位** | 各車輪のESC（電子制御ブレーキ）、EPS（操舵）、ECU | ABS（アンチロックブレーキ）、横滑り防止、操舵角のフィードバック制御、衝突時のエアバッグ展開 |

**通信**: CANバス / Automotive Ethernet

- 上位が「前方30mで歩行者が横断しそうだから減速しろ」と指示
- 下位が「タイヤの滑りを監視しながら、10ms周期でブレーキ油圧を調整」
- 上位のソフトウェアがクラッシュしても、下位のABSは常に動作し続ける

### 例4: 自家用・研究用（Raspberry Pi 5 + Arduino / Teensy）

ユーザー様がこれから構築される可能性のある構成です。

| 層 | ハードウェア | 行っていること |
|----|-------------|-------------|
| **上位** | Raspberry Pi 5 | OpenCVによる物体検出、ROS2でのナビゲーション計画、SLAM、音声認識 |
| **下位** | Arduino Nano / Teensy 4.1 / STM32 | モーターPWM出力、エンコーダ読み取り、IMUデータ取得、緊急停止スイッチ監視、PID制御 |

**通信**: USBシリアル / UART / I2C / ROS2（micro-ROS）

- 上位が「カメラで見つけた赤いボールの方向へ進め」と目標値を送信
- 下位が「IMUとエンコーダを見ながら、1msごとに左右モーターの回転数を調整」
- 上位が画像処理で高負荷になっても、下位は「転倒しない・壁にぶつからない」を保証

### 4つの例の共通点

| 上位（脳） | 下位（脊髄・反射） |
|-----------|------------------|
| 「何をするか」を決める | 「どう動かすか」を実行する |
| 100ms〜1s 単位の処理 | 1ms〜10ms 単位の処理 |
| 重いAI・画像処理 | 軽いPID・安全監視 |
| フリーズしても致命的ではない（復帰可能） | フリーズは致命的（即座に安全動作へ） |

## 計算機特徴

上位計算機と下位計算機を、**「脳」と「脊髄・反射神経」** の比喩で整理します。

### 上位計算機：「脳」

**役割**: 周囲の状況を理解し、「何をすべきか」を判断する

| 特徴 | 説明 |
|------|------|
| 処理内容 | 画像認識、SLAM、経路計画、AI推論、音声認識 |
| 許容遅延 | 数十〜数百ms 程度でも問題ない |
| OS | Linux（Ubuntu、Raspberry Pi OS）など、フル機能のOS |
| 言語 | Python、C++、ROS2 |
| 弱点 | GCや重い処理で一時的に応答が遅れることがある |

**代表的な計算機の例**:

| 計算機 | 用途 | 特徴 |
|--------|------|------|
| **NVIDIA Jetson Orin** | 自律移動ロボット、ドローン | GPU搭載、AI推論が高速 |
| **Raspberry Pi 5** | 教育・研究用ロボット | 安価、Linux完備、カメラ接続が容易 |
| **x86 産業用PC** | 工場の産業ロボット | 長期安定動作、EtherCAT等の産業用I/F |
| **Raspberry Pi 4/5 + Coral TPU** | エッジAI搭載ロボット | 低消消費電力で軽量AI推論が可能 |

### 下位計算機：「脊髄・反射神経」

**役割**: 脳からの指示を受けて、体を正確かつ安全に動かす

| 特徴 | 説明 |
|------|------|
| 処理内容 | モーターPID制御、センサー読み取り、緊急停止、安全監視 |
| 許容遅延 | **1ms〜10ms単位**で必ず応答が必要 |
| OS | リアルタイムOS（FreeRTOS等）またはベアメタル（OSなし） |
| 言語 | C/C++（決定的な処理時間が保証できる） |
| 強み | 上位がフリーズしても、安全動作を継続できる |

**代表的な計算機の例**:

| 計算機 | 用途 | 特徴 |
|--------|------|------|
| **STM32（F4/H7シリーズ）** | 産業ロボット、ドローンFC | リアルタイム性が高い、タイマーが豊富 |
| **Teensy 4.1** | 研究用ロボット、音響機器 | 600MHz、Arduino互換、GPIOが高速 |
| **Arduino Nano / Uno** | 教育・小型ロボット | 安価、シンプル、入門向け |
| **ESP32** | Wi-Fi/Bluetooth必要なロボット | 無線通信と制御が1つで可能 |
| **Pixhawk（STM32F4）** | ドローン専用FC | PX4ファームウェア対応、センサー統合済み |

### 比喩で見た分担

| 状況 | 上位（脳） | 下位（脊髄） |
|------|-----------|-------------|
| ドローンが赤い標的を追う | 「あの赤い物体を追跡せよ」と目標速度を計算 | 1msごとに4つのモーター回転数を調整し、姿勢を保つ |
| アームが部品を掴む | カメラで部品位置を認を認識し、掴む軌道を計算 | 各関節のモーターを0.1ms周期で追従させる |
| AGVが人を避ける | LiDARで人を検知し、回避経路を生成 | 即座にブレーキをかけ、衝突を物理的に防ぐ |
| 四足歩行が坂を登る | カメラで地形を認認識し、歩行パターンを決定 | 各足の力覚を1000Hzで監視し、滑りを即座に補償 |

### ユーザー様が構築しうる構成の例

現在の Raspberry Pi 5 を軸にした場合：

```
┌─────────────────────────────────────┐
│  Raspberry Pi 5（上位・脳）          │
│  ・カメラ画像処理（OpenCV）          │
│  ・SLAM / ナビゲーション計画         │
│  ・ROS2 で経路生成                   │
└──────────────┬──────────────────────┘
               │ USB/UART
┌──────────────▼──────────────────────┐
│  Arduino / Teensy / STM32（下位・脊髄）│
│  ・ICM-20948 から姿勢取得（EKF）     │
│  ・モーターPWM出力（PID制御）        │
│  ・緊急停止スイッチ監視              │
│  ・バッテリー電圧監視               │
└──────────────┬──────────────────────┘
               │
        [モータードライバ・サーボ]
```

このように分けることで、Pi 5 が画像処理で高負荷になっても、**下位計算機が姿勢を保ち、転倒や暴走を防ぎます**。
